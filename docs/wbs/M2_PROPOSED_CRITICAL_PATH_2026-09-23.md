# Wanderloom M2 Critical Path — 2026-09-23

## Status

Accepted. This document supersedes the provisional status of the M2 plan.

## M2 objective

M2 is the **Solo Progression Slice**: deepen the M1 solo loop with explicit failure risk, progression, rarity, multiple expedition choices, equipment feedback, reproducible balance measurement, and end-to-end acceptance.

## Accepted product decisions

1. **Rarity:** all seven labels are part of the M2 contract: Common / Uncommon / Rare / Epic / Legend / Mythic / Phantasm. Initial M2 zones may make upper rarities extremely rare or unreachable by configuration.
2. **Failure consequence:** failure affects value generated by the current expedition. Gold/EXP retention is policy-driven; newly generated drops may be lost. Existing owned/equipped items are not directly lost in M2.
3. **Existing equipment loss:** deferred to a later high-risk exploration design together with protection/recovery rules.
4. **Risk choice:** both zone and duration are supported contract dimensions.
5. **OIDC / appDataFolder:** outside the M2 gameplay critical path; they remain parallel/post-M2 work.
6. **Balance values:** Gold/EXP retention percentages are not fixed in CP-20. They remain explicit loss-policy inputs and will be tuned using CP-24 measurements.

### CP-20 — Failure / drop-loss domain contract

Scope is `packages/game-core` only for the first checkpoint. Worker, D1, and Web integration are excluded.

Required contracts:
- `ExpeditionOutcome = success | failure`
- explicit `LossPolicy`
- `FailureResolution` separating retained and lost Gold/EXP/drops
- `ExpeditionRiskPreview` separating failure probability from loss consequence
- deterministic resolver compatibility: same character snapshot + zone/duration + configuration + seed must produce the same outcome/reward/loss once seeded failure resolution is wired
- M1 success behavior remains valid

Checkpoint acceptance:
- success and failure are representable without runtime coupling
- loss policy is input/configuration, not a hard-coded balance target
- current-expedition generated drops can be lost without exposing existing inventory/equipment to loss
- probability and consequence remain separate concepts
- domain tests pass and M1 success-path tests remain green

### CP-21 — Growth / progression
Deterministic EXP/level progression, guards, serialization, and exactly-once application.

### CP-22 — Rarity + multi-zone reward model
Seven-rarity contract, zone + duration configuration, shared preview/resolution configuration, deterministic rarity/drop generation.

### CP-23 — Equipment effects → exploration
Freeze equipped effects into exploration-start state; later equipment changes cannot rewrite an active expedition.

### CP-24 — Balance simulation harness
Seeded batch simulation using production game-core functions; report success/failure, Gold/EXP EV, rarity/drop frequencies, and progression rate. Outputs before tuning are measurements, not accepted targets.

### CP-25 — M2 API/UI integration
Expose risk preview, result, progression, rarity, and equipment feedback through the existing low-bandwidth shell without moving authority to the client.

### CP-26 — Migration/concurrency regression
Snapshot migration/round-trip, claim/equip/progression retries, failure atomicity, stale-version regressions, and retained M1 real-D1 acceptance.

### CP-27 — Full M2 acceptance
End-to-end: compare choices → preview risk/reward → start with frozen state → success/failure → atomic claim → reward/loss + progression → inspect/equip rarity item → start again with changed effective stats.

## Parallel / post-M2

OIDC/account linking, Google appDataFolder/archive synchronization, monetization, Party, Caravan, and AI features remain outside this critical path.
